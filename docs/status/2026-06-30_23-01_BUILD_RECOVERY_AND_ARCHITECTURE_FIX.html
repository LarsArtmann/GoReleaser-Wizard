The project was in a blocked state: a previous dependency refactor (commit 8b1440f) replaced a working hasFile function with non-compiling code (slices.Contains(dirs, nil)), which cascaded into 4 of the 5 buildflow failures. The 5th failure — nix-build — was caused by a deeper architectural problem: the domain layer performed filesystem I/O (exec.LookPath) during validation, which failed inside the Nix sandbox where signing tools (gpg, cosign) are not installed.

Both root causes are now fixed. The build is fully green. This report documents the current state, the remaining gaps, and the prioritized path forward.

01Root Causes (Both Fixed)

Fixed · Root Cause 1

Broken hasFile helper blocked compilation

internal/utils/recommendations.go:98

Commit 8b1440f ("use slices package instead of manual directory traversal") replaced the working implementation with func hasFile(filename string) bool { return slices.Contains(dirs, nil) } — a one-liner that references an undefined variable dirs, doesn't use the filename parameter, and cannot compile. This single breakage cascaded into test-race, test-coverage, go-fix, and govalid-generate — all of which depend on a successful build.

Fix applied: Restored the original os.Stat-based implementation that checks the current directory plus common subdirectories (cmd, pkg, internal, src, app). Removed the now-unused slices import.
Fixed · Root Cause 2

Domain layer performed filesystem I/O during validation

internal/domain/config_core.go:288 & internal/validation/business_rules.go:398

The domain layer's validateSigningConfiguration() called exec.LookPath(tool) to verify signing tools (gpg, cosign, openssl) were installed. This violated the project's own documented architecture rule — "domain layer must not use external dependencies" — and broke the Nix sandbox build, where those tools don't exist. Integration tests that enable basic signing (SigningLevelBasic) failed with EXTERNAL_TOOL_NOT_FOUND.

Fix applied: Removed the filesystem check entirely from the domain layer (signing-level enum validity was already checked separately at config_core.go:136). In the validation layer, downgraded the duplicate tool-availability check from a blocking error to a warning — signing tools are needed at release time in CI, not at config-generation time.

05Totally Fucked Up (Now Fixed)

The 8b1440f refactor was sabotage-by-automation

A commit titled "use slices package instead of manual directory traversal" replaced 15 lines of working os.Stat logic with a single line that does not compile. The replacement slices.Contains(dirs, nil) referenced an undefined variable, ignored its input parameter, and returned a constant regardless of whether any file existed. This shipped to master and broke the build for an unknown period.

Lesson: No build/CI gate caught this before merge. The hasFile function has no direct unit tests, so a nonsensical rewrite passed review. This function needs tests now.

Domain layer violated its own purity rule

The most important architectural rule in this project — "domain must be pure, zero external dependencies, no side effects" — was violated by the domain layer itself calling exec.LookPath(). This wasn't a new mistake: it was sitting in the codebase, silently breaking the Nix sandbox build, until someone ran nix build.

06What We Should Improve

  • Add a pre-commit/pre-merge build gate — a broken hasFile should never reach master. The buildflow --fix run exists; it should run on every push.
  • Add unit tests for hasFile — the function that just broke the build has zero direct tests. This is the highest-ROI test addition possible.
  • Enforce domain purity mechanically — go-arch-lint catches import violations but not behavioral ones (like calling exec.LookPath). Consider a custom linter rule or a domain test harness that runs in a hermetic environment.
  • Consolidate documentation sprawl — 16 root-level .md files (4,914 lines) plus 20+ status reports. Most are point-in-time snapshots that belong in docs/ or should be archived. Root should contain only living docs (README, AGENTS, FEATURES, TODO_LIST, ROADMAP, CHANGELOG).
  • Raise domain coverage from 10% to 80%+ — the domain layer is the easiest code to test (pure functions, no I/O) and the most important to get right.
  • Fix the 16 makezero lint warnings — slices created with make([]T, len(x)) followed by append waste capacity. Use make([]T, 0, len(x)) instead. Trivial, mechanical fix.
  • Distinguish "config generation" vs "release readiness" validation — the signing-tool check confusion shows these two concerns are conflated. Config generation should validate correctness; release readiness should check environment.

09Top Question I Cannot Answer Myself

Should signing-tool availability ever block, and if so — at which stage? ANSWERED: warning-only at generation time; blocking release-readiness check routed to ROADMAP.md (2026-11-07)

I downgraded the signing-tool check from a blocking error to a warning in the validation layer, and removed it entirely from the domain layer. My reasoning: at config generation time, the user is producing a .goreleaser.yaml — they don't need gpg or cosign installed locally; those run in CI at release time. Blocking config generation because a local tool is missing seemed wrong, and it broke the Nix sandbox build.

But I can't determine the intended product behavior: Should the wizard offer a separate "release readiness check" command that DOES block on tool availability (a pre-flight check before goreleaser release)? Or is the warning sufficient and the user is expected to install tools before releasing? This is a product/UX decision, not a technical one — and it determines whether the validation architecture needs two distinct passes or one.

Awaiting decision: Keep warning-only (current), or add a separate blocking goreleaser-wizard check command for release-time environment validation?
